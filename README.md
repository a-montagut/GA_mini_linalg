# 4. Numerical precision and stability: exploring the Roofline model

Benchmark of dense matrix-vector multiplication (`y = A x`) and
matrix-matrix multiplication (`C = A B`) with NumPy in `float32` (single
precision) and `float64` (double precision), interpreted with the Roofline
model. NumPy hands both operations to the BLAS library (routines GEMV and
GEMM of OpenBLAS).

## Contents

| File | Purpose |
|---|---|
| `kernels.py` | The two operations, array initialisation, correctness check, and the theoretical FLOP / byte / arithmetic-intensity models |
| `benchmark.py` | Timing driver: sweeps the problem size `N` for both precisions, plus a bandwidth probe (copy/add of 256 MB arrays). Writes `results/bench_<tag>.csv`, `results/machine_<tag>.json` |
| `plot_results.py` | Builds the figures in `figures/` (time and speed-up, GFLOP/s and GB/s, Roofline) and prints the summary tables (see [Reading the tables](#reading-the-tables)) |
| `results/` | Measurements used in the report (`1t` = one BLAS thread, `allt` = all threads), the run logs (`log_*.txt`), `tables.md` (the printed tables in Markdown) and `plot_output.txt` (the full printed output) |
| `figures/` | Generated plots (`.pdf` for the LaTeX report, `.png` for Word and quick viewing) |
| `report/` | The technical report: `Report_Roofline.pdf`, `.tex` and `.docx`, all generated by `report/build_report.py` |
| `context/` | The homework statement and the lecture slides, kept locally for reference. **Not committed** (listed in `.gitignore`); nothing in the project depends on it |

## Requirements

Python 3.10+ with `numpy`, `pandas` and `matplotlib`:

```bash
pip install numpy pandas matplotlib
```

Rebuilding the report also needs `python-docx` (`pip install python-docx`)
and, for the PDF, a LaTeX installation with `pdflatex`.

## Reproducing the results

```bash
python benchmark.py                # all BLAS threads  -> results/bench_allt.csv
python benchmark.py --threads 1    # one BLAS thread   -> results/bench_1t.csv
python plot_results.py             # figures/*.pdf, figures/*.png, results/tables.md
python report/build_report.py      # report/Report_Roofline.tex, .pdf, .docx
```

`python benchmark.py --quick` runs only the small sizes (a few seconds) to check
that everything works. `--min-time` and `--min-reps` control how many timed
repetitions are taken per point (defaults: at least 5 repetitions and at
least 0.5 s of accumulated timed work).

A full run takes a few minutes per thread setting and needs about 3.5 GB of
free memory (the largest matrix-vector case is a 16384 x 16384 `float64`
matrix).

**Run both settings back-to-back, on mains power, with other applications
closed.** The clock of this laptop processor moves between 1.9 GHz (base)
and 4.2 GHz (turbo) with power, temperature and background load, so results
vary between runs: over five all-threads runs the best `float32`
matrix-matrix result ranged from 174 to 312 GFLOP/s. The single-thread run
varies much less. The numbers in the report text are written by hand in
`report/build_report.py` and match the run in `results/` (14 Nov 2026), so
they must be updated after a new run.

## Terminology

The terms follow the lecture slides:

* **cache**: the 8 MB last-level (L3) CPU cache, shared by the four cores.
  A problem *fits in cache* when its whole working set (A + x + y) is at most
  8 MB.
* **main memory**: the DDR4 memory behind the cache, with theoretical
  bandwidth *B_mem* = 38.4 GB/s.
* **memory-bound / compute-bound**: performance limited by *B_mem* times the
  arithmetic intensity *I*, or by the peak arithmetic rate *P_peak*.

## Reading the tables

`python plot_results.py` prints four tables and also saves them to
`results/tables.md`. Every value carries its unit. The **1-thread run**
(`results/bench_1t.csv`) is the main evidence for scaling and for the
cache-versus-main-memory effect: one core, no thread start-up cost, and the
smallest run-to-run spread. The all-threads run is used for peak performance
and the Roofline figures. Tables 2 and 3 show both runs.

Common terms:

* **N**: matrix size (A is N x N). Each row is about sqrt(2) times larger
  than the one before.
* **work**: floating-point operations per call: 2N^2 for matrix-vector,
  2N^3 for matrix-matrix.
* **performance**: work / median time, in GFLOP/s.
* **bandwidth**: the minimum (compulsory) data moved per call divided by the
  median time, in GB/s. This is the *estimated* traffic; the actual traffic
  can be higher.
* **f32 / f64**: `float32` / `float64`.

### Which table answers which homework question

| Question | Evidence |
|---|---|
| Q1: How does time scale with N? | Tables 1 and 2 |
| Q2: matrix-vector vs matrix-matrix (arithmetic intensity, data reuse) | Table 1 (performance columns), Table 4, Roofline figure |
| Q3: float64 vs float32 | Table 1 (f32 vs f64 columns), Table 3 |
| Q4: Unexpected results | Spread column in Table 3, small-N rows in Table 1 |

### Table 1: execution time vs problem size (1 thread)

One table per operation. For each precision it gives the median time per
call, the **growth** (time divided by the time of the previous row), and the
performance.

How to read it: N grows by sqrt(2) per row. If time is proportional to the
work, growth should be **x2.00** for matrix-vector (N^2) and **x2.83** for
matrix-matrix (N^3), and performance should stay flat.

Key findings:

* Matrix-matrix grows by about x2.5 to x3.2 per row from N = 256 upwards,
  with performance flat at 75-91 GFLOP/s (f32) and 38-44 GFLOP/s (f64).
* Matrix-vector grows by about x1.9 to x2.3 per row from N = 5,793 on
  (matrix in main memory), with performance flat at about 10 GFLOP/s (f32)
  and 4.5 GFLOP/s (f64).
* For small N, growth stays below the expected value: each call has a fixed
  cost of a few microseconds, which is larger than the arithmetic itself.

### Table 2: fitted scaling exponent

A straight-line fit of log(time) = p log(N) + c within each regime. A fitted
**p** close to the expected one means time grows linearly with the work.

| 1 thread | fitted p | expected |
|---|---|---|
| matrix-vector, data in main memory | 2.21 (f32), 2.17 (f64) | 2 |
| matrix-matrix, N >= 256 | 3.01 (f32), 3.01 (f64) | 3 |
| matrix-vector, data fits in cache | 1.69-1.76 | 2 (lower because of call overhead) |

The matrix-vector value is slightly above 2 because performance keeps
falling a little between 8 and 64 MB (see Table 3).

### Table 3: matrix-vector speed, cache vs main memory

One table per precision. Each row gives the working-set size, where it
lives, and the bandwidth, performance and **spread** for both thread
settings.

* **spread** = (median time - best time) / median time. Below about 15 %
  the point is reproducible; above about 30 % it is noisy and should be
  given less weight.

Key finding: performance drops when the matrix outgrows the cache, but
gradually rather than in one step. For f64 with 1 thread: 9.4 GFLOP/s at
N = 724 (4 MB, cache), then 7.7 (8 MB), 6.2 (16 MB), 5.2 (32 MB) and
4.5 GFLOP/s from 128 MB on (main memory). Matrix-matrix has no such drop:
BLAS splits it into blocks that fit in cache and reuses every block many
times.

### Table 4: cache vs main memory summary (matrix-vector, 1 thread)

The median bandwidth of all matrix-vector sizes in each group.

| data lives in | f32 | f64 |
|---|---|---|
| cache | 35.7 GB/s | 36.4 GB/s |
| main memory | 21.0 GB/s (59 %) | 18.9 GB/s (52 %) |

Matrix-vector multiplication reads each element of A once and uses it in
one multiply-add (0.25 FLOP/byte for f64, 0.5 for f32). It is therefore
memory-bound, and its speed is set by where the data lives. From main
memory it gets about half the in-cache bandwidth, and about half of the
theoretical 38.4 GB/s.

### float32 vs float64 (from Tables 1 and 3)

At large N, float32 is about **2x faster** for both operations, for two
different reasons:

* **matrix-vector** (memory-bound): float32 moves half the bytes
  (measured 2.1-2.8x, 1 thread, N >= 1,024).
* **matrix-matrix** (compute-bound): an AVX2 instruction processes 8 floats
  instead of 4 doubles (measured 1.9-2.3x, 1 thread, N >= 256).

## Measurement methodology

* Arrays are created with `np.full` (constant values, as in the statement)
  **before** timing; outputs are pre-allocated and written with `out=`, so
  neither allocation nor initialisation is inside the timed region.
* Two untimed warm-up calls per configuration (caches, BLAS thread pool).
* Each point is repeated until at least `--min-reps` calls and `--min-time`
  seconds have been timed with `time.perf_counter`; the **median** is
  reported (the minimum is stored too).
* `float32` and `float64` are run back-to-back for each `N` so that both see
  the same thermal/clock state of the machine.
* Results are checked against the exact answer (`y_i = 3N`, `C_ij = 2N`)
  with a tolerance-based comparison, never exact equality.
* GFLOP/s = `2N^2 / t` (matrix-vector) or `2N^3 / t` (matrix-matrix).
  Effective bandwidth uses the *compulsory* traffic (each array moved once):
  `(N^2 + 2N) s` (matrix-vector) and `3 N^2 s` (matrix-matrix), with
  `s` = 4 or 8 bytes.

## Hardware used for the reported results

Dell Latitude 7490, Intel Core i7-8650U (4 cores / 8 threads, 1.9 GHz base,
up to 4.2 GHz turbo, 15 W, AVX2 + 2 FMA units per core, 8 MB L3 cache),
2 x 8 GB DDR4-2400, Windows 11, Python 3.14, NumPy 2.5 with OpenBLAS 0.3.34.
The theoretical Roofline uses a compute ceiling band from base clock
(121.6 / 243.2 GFLOP/s for float64 / float32) to maximum turbo
(268.8 / 537.6 GFLOP/s), and B_mem = 38.4 GB/s. These constants are at the
top of `plot_results.py`; change them when running on a different machine.
